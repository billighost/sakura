# Sakura performance review and approved implementation plan

Audit date: 12 November 2026. Baseline application: `5229fdb1484cea3282e9951f1905b6e3716e2bf4`.

This plan was written after ten independent, read-only subsystem audits and primary-agent verification of the important paths. The user subsequently authorized full implementation after the plan was written. No deployment, push, production migration, or external configuration is authorized.

## Executive assessment

Sakura has a substantive performance foundation. The previous overhaul really implemented shared provider flights, lightweight bootstrap, account-scoped resource caches, exact faster sequencing, isolated playback clocks, prepared audio handoff, progressive verified downloads, lazy player/world code, responsive artwork, public-only Redis and complete Bloom preparation. Repeating those changes would add risk without addressing the remaining bottlenecks.

The remaining opportunities concentrate at subsystem boundaries: optional work still gates usable responses; independent page and synchronization requests repeat projections and contend for an exclusive account lock; some advertised cache limits cover retained entries but not active allocations; download updates reach unrelated React consumers; and long-lived offline journals grow even when their visible state is compact. No demonstrated P0 outage was found. There are multiple P1 opportunities affecting first interaction, large libraries, concurrent playback and constrained devices.

Cold and warm behavior differ materially. Warm navigation, ready audio, L1 metadata and already transformed lyrics benefit from the previous pass. Cold resource delivery through the service worker, cold dictionary/codec/provider initialization, complete collection canonicalization and Bloom sample generation still incur work that those warm caches cannot remove. Mature-account and multi-tab behavior is insufficiently represented by current fixtures.

Fixture timings are not deployed latency or production percentiles. Independent tests overlap and must not be summed into a unique total.

The local checkout initially was clean on master at `5229fdb`; read-only `git ls-remote` confirmed GitHub master at the same SHA. Root AGENTS.md was the only applicable repository instruction file. ## Policies fixed by the user

1. Keep current Saved behavior, including completed next-song acquisition. Improve obsolete-work cancellation and priority without silently demoting completed files.
2. Keep the 15-second passive synchronization freshness target. Coalesce duplicate triggers and tabs rather than increasing the interval.
3. Keep current false-online/offline fallback timing. Overlap safe local reads but do not introduce a shorter fallback deadline.
4. Preserve complete Bloom soundtrack readiness, existing audio integrity, account isolation, privacy/erasure fences, queue occurrences and authored visual quality.
5. Conditional work below starts with measurement. Do not make a speculative architectural change solely because it appears in this plan.

1. Freeze code/test provenance and preserve concurrent changes. Repair versioned fixtures, build the baseline, record real current browser metrics and unit/count microbenchmarks. No live writes for baselines.

## Deliberately retained or rejected

Do not reduce bcrypt/authentication, cache deleted-account success, put private projections/audio/tokens/drafts into Redis, weaken hashes/versions/scopes, remove erasure/tombstones without causal replacement, truncate ranking reservoir/profile/export, bypass ownership fences/chat serialization, increase pool/global transfer limits blindly, or mark incomplete audio Saved. Preserve current Saved and15-second/fallback policies explicitly chosen by the user.

Do not globally disable Next Link prefetch or move every private screen into server rendering to use PPR. The existing partial shell and neutral offline renderer are intentional. Do not blanket replace provider-native images with next/image, strip authored SVG/world detail, reduce manual quality, or change the950ms illustrated prelude merely to lower a benchmark. Measure intentional motion separately from blocked work.

Cold Telegram/bot production, transfer of complete verified bytes, tokenizer initialization, proof-of-work, hosted GPU/model/inference quotas, browser codec/encoding support, physical audio latency and OS background suspension are real limits. Code can avoid duplication, hide safe latency and manage resources; it cannot promise instant completion of those external costs.
