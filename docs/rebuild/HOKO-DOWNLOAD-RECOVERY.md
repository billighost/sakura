# HOKO playback and download recovery

The real Sakura search API returned both TOMONARI SORA entries: `咆哮` (Spotify `7rc79XVkUIvmK4TINjXhl1`) and `咆哮 - HOKO` (Spotify `1fPkUiufkRpzdYcBKXUP3s`). Both share canonical recording `6e9e1881-12b4-4892-8aa7-39baea79e89b` and ISRC `JPB602501985`.

Repeated production resolution jobs failed after exactly 50 seconds, leaving no stored audio asset. A fresh metadata-only trace identified the sequence: the original source lookup returned a localized-title mismatch at 25.409 seconds; exact catalogue and artist alias hydration took another 12.937 seconds; a repeated localized spelling took 12.100 seconds. The verified `HOKO` / `友成空` spelling was consequently attempted only at 50.448 seconds, after the production discovery deadline. That lookup succeeded 2.527 seconds later. Earlier startup checks used a 65-second direct discovery call and never persisted its source, which hid this production-path failure.

Source recovery now prioritizes independently verified alternate artist/title spellings, reuses persisted native proof, and bounds individual recovery requests. Resolution jobs share a 110-second transfer-work budget, with up to 90 seconds for discovery and preparation limited to the remaining budget. This fits the existing 115-second job lease and 125-second client polling window. Identity, version, audio-size, and checksum verification remain enforced.

Explicit failed download retries and playback retries now bypass stale source caches. Downloads retain verified chunks when the refreshed fingerprint matches and discard old chunks when it changes. Audio error responses preserve recognized application reasons through bounded JSON parsing, preventing a missing source from being mislabeled as a connection interruption.

Live verification used Sakura's actual search, resolve, job-polling, and authenticated audio APIs on a local Next.js server. A test-only fetch guard refused unbounded upstream audio requests, including automatic full-file preparation. Both titles resolved successfully. The server returned `206` with exact ranges `bytes 0-4095/8828274` and `bytes 4096-8191/8828274`, matching audio MIME and ETag. Total received song audio was **8,192 bytes**. No complete real song was downloaded or checksum-certified by this limited check; generated local audio regressions exercise complete-save verification separately.

Regression evidence is maintained in `src/rebuild/server/server.test.ts`, `scripts/rebuild-download-engine.test.ts`, `scripts/rebuild-playback-integration.test.ts`, and `scripts/rebuild-errors.test.ts`. Verification passed the full project TypeScript check, all 96 server regressions, the complete `npm run test:downloads` suite including 48 worker tests, eight focused error tests, and 14 browser checks for complete generated-audio saves, interruption, Retry, offline playback, and mobile layouts with zero page errors. Targeted ESLint checks passed. The private live traces and low-data guard are retained under `.local/hoko-*` and excluded from source control.
