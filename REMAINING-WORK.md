## Shared Context

*Every prompt references this section. Read it before starting.*

### Design language

Four rules the redesign holds to. Breaking one is a bug, not a style opinion.

1. **No decorative gradients.** Colour comes from flat, tonally-related
   surfaces that step by luminance. Exactly two gradients are permitted, both
   functional: readability scrims over artwork (one colour, ramping opacity),
   and the skeleton shimmer sweep. Two-stop pink→purple fills, radial hero
   blobs, and 135° accent ramps are the loudest "generated by a machine" tell
   and they are gone — don't reintroduce them.
2. **Surfaces step, they don't float.** Four elevation levels, each a real
   colour rather than a translucent white overlay. Blur only where content
   genuinely scrolls underneath (app chrome).
3. **Motion has physics.** Use the named curves. Press states are instant in,
   sprung out. Nothing shares a generic hover-spin.
4. **One accent.** Sakura pink marks the active thing and nothing else.

### Tokens (`src/app/globals.css`)

```
Colour     --bg  --surface-1..4  --text --text-2 --text-3
           --line --line-strong
           --accent --accent-press --accent-soft --accent-softer --on-accent
           --danger/-soft  --success/-soft  --warning/-soft
           --chrome --chrome-line --scrim  --shadow-1..4
           --skeleton --skeleton-hi
Type       --font-display (Fraunces) --font-body (Inter)
           --t-2xs --t-xs --t-sm --t-base --t-md --t-lg --t-xl --t-2xl --t-3xl
           --lh-tight/snug/normal/loose
           --track-tight/snug/wide/caps
Radii      --r-xs --r-sm --r-md --r-lg --r-xl --r-2xl --r-full
Motion     --ease --ease-in-out --ease-out --spring --spring-soft
           --d-instant --d-fast --d-base --d-slow --d-slower
Layout     --space-1..7  --gutter  --tap-min
           --tabbar-h --miniplayer-h --bottom-chrome  --art-max
           --ui-density  (shrinks on short viewports; read it, don't fight it)
```

**Type is semantic:** if it's the *name of a thing* (track title, artist, page
heading) it's `--font-display`. If it's an instruction, label or number, it's
`--font-body`. That split is what keeps the app feeling edited.

### Utilities

`.pressable` / `.pressable-lg` (the main interaction primitive — any tappable
non-link surface should carry it), `.anim-stagger` (set `--i` per child,
capped), `.skeleton`, `.truncate`, `.clamp-2`, `.snap-x`, `.no-scrollbar`,
`.eyebrow`, `.srOnly`, `.tapTarget`.

Keyframes available globally: `fadeIn`, `slideUp`, `slideDown`, `scaleIn`,
`pulse`, `sheen`.

### Legacy alias layer

~40 stylesheets still reference `--sakura-*`. Those names are re-pointed at the
new palette in `globals.css`, so untouched files inherit the new colours for
free. **`--sakura-accent-gradient` now resolves to a flat accent.** When you
rewrite a file, migrate it to the short token names.

### Icons (`src/components/Icons.tsx`)

- Never `<svg>` inline in a page. Import from `@/components/Icons`. If a glyph
  is missing, add it there.
- No two icons share a path. No emoji anywhere, ever — including canvas text
  (use `drawBlossom` / `drawWordmark` from `src/lib/brandMark.ts`).
- Animation: parts carry `data-part="…"`, keyframes live in
  `Icons.module.css`, and an ancestor with `[data-anim]` triggers them. Add a
  new part + its own physical keyframes rather than reusing a spin.
- `NowPlayingBars` is a live state readout (dances / freezes low when paused).
- Genre scenes accept `tone` for a second colour.

### Known trap

`all: unset` resets `position` to `static`. If a rule does `all: unset` and
elsewhere has an absolutely-positioned `::before` sized `max(100%, 44px)`, that
pseudo-element anchors to the nearest *positioned ancestor* and inflates to
that box — an invisible full-container shield that eats every tap. This is
exactly what made the mini player unusable. Always put `position: relative` on
the same rule that defines the pseudo-element.

### House style

- Match the surrounding code's comment density. This codebase comments the
  *why* — especially the non-obvious tradeoff or the bug a line prevents. Keep
  that. Don't narrate the obvious.
- Server state: read the actual API shape before assuming it. Several
  endpoints return a bare array, not `{ items: [...] }`.
- Never ship a control that doesn't do anything. If a toggle has nothing to
  wire to, delete it and say so.
- Every interactive element: real ≥44px target, `aria-label` where the label
  isn't text, keyboard reachable, visible focus.
- Errors are states, not silence. A failed fetch must produce something the
  user can act on.

### Verify before you finish

```bash
npx tsc --noEmit
npx eslint <files you changed>
```

`<img>` warnings are pre-existing across the codebase and fine. Zero errors.

# Phase 1 — Interaction foundation

*Do this first. Later phases build on the primitives it establishes.*

## Prompt 1.1 — Motion & gesture system

```
Read § Shared Context in REMAINING-WORK.md first.

Build the shared interaction layer this app is missing. Right now every
component invents its own transition, and gestures give almost no feedback —
you can't tell whether a swipe registered until it's over.

Create a small set of reusable primitives (hooks and/or components — your
call on the shape) covering:

- Press feedback that feels physical, beyond what .pressable does today.
- Swipe / drag gestures with live visual feedback while the finger is down:
  the user should see the commit threshold approaching, not just find out
  afterwards. There's a working reference in MiniPlayer.tsx (axis locking,
  velocity, rubber-banding) — factor out what's genuinely shared rather than
  forcing every caller into one shape.
- Long-press with a progress indication.
- Pull-to-refresh (src/lib/usePullToRefresh.ts + PullToRefreshSpinner.tsx
  already exist — assess and improve rather than replacing outright).
- Sheet/modal presentation: consistent enter/exit, drag-to-dismiss with
  rubber-banding, backdrop, scroll locking, focus trapping, Escape.
- Haptics: src/lib/haptics.ts exists. Give it a semantic vocabulary
  (selection / impact / success / warning) instead of raw millisecond
  numbers scattered through call sites, and make every gesture commit fire
  the right one.

Constraints that matter: transform/opacity only so it stays on the
compositor; honour prefers-reduced-motion (movement and loops off, opacity
fades kept); never leave a stuck :hover state on touch.

Then adopt the primitives in MiniPlayer, FullPlayer, QueueModal,
ContextMenu, ShareModal, PlaylistModal and AddToPlaylistModal so there's one
motion language rather than seven.

Document the vocabulary briefly at the top of whatever file holds it, so the
next person picks the right primitive instead of adding an eighth.
```

## Prompt 1.2 — App-shell chrome & page transitions

```
Read § Shared Context in REMAINING-WORK.md first.

Make this feel like an installed app rather than a website in a phone
browser. Files: src/app/(app)/layout.tsx, layout.module.css,
src/components/TabBar.tsx, Header.tsx, and the shared page scaffolding.

- One header primitive that every page uses: large title that collapses into
  a compact sticky bar on scroll, optional back button, optional actions.
  Right now Settings hand-rolls its own back button — that should come from
  the primitive.
- Correct safe-area handling in standalone PWA mode (no browser chrome to
  fall back on).

Then migrate the pages to the header primitive. Note some pages are server
components — keep the split clean.
```

# Phase 2 — Lyrics

## Prompt 2.1 — Lyrics scroll behaviour & highlight

```
Read § Shared Context in REMAINING-WORK.md first.

Rework the lyrics view. Files: src/components/LyricsModal.tsx +
LyricsModal.module.css. Timing data comes through PlayerContext
(lyrics, activeLyricIndex); src/lib/lyrics.ts has the LyricData shape.

Two problems.

1. Scroll is a straitjacket. It force-scrolls to the active line on every
   index change, so you cannot read ahead or look back — the moment you
   scroll away it yanks you back. Make it work the way Spotify does:
   - The user can scroll freely at any time; auto-scroll yields immediately.
   - It resumes on its own, and getting the resume conditions right is the
     interesting part. Consider: idle time since last touch, whether the
     active line has come back into view, whether the user scrolled far away
     vs. nudged, and what should happen on seek or track change (those should
     snap, not drift). Think about what feels right rather than implementing
     a single timeout.
   - While detached, offer a way back — something like a "jump to current"
     affordance that appears only when it's useful.
   - Momentum scrolling must not be interrupted mid-flick.

2. The active line highlights its whole background as a block, which looks
   like a selected table row. Only the *text* should carry the highlight.
   Make the active line read as active through type treatment — weight,
   colour, scale, opacity of neighbours — not a background fill. If the
   lyrics are word-synced, use that: highlight should travel through the
   line as it's sung. Check whether the data has word timings before
   assuming.

Also: lines are click-to-seek but there's no indication they're
interactive, and the per-line share button is always visible on every line,
which is noisy.
```

## Prompt 2.2 — Transliteration on demand

```
Read § Shared Context in REMAINING-WORK.md first.

Songs in non-Latin scripts sometimes arrive with a transliteration and
sometimes don't (LyricData carries an optional `transliterated` per line —
see src/lib/lyrics.ts and src/app/api/lyrics/route.ts, which uses
@stef-0012/synclyrics).

Add a way for the user to request one when it's missing: a control at the
top of the lyrics view that generates transliteration for the current track.

Design decisions to make (not prescribing):
- Only offer it when it makes sense — showing "Get transliteration" on an
  English song is noise. Work out how to detect script from the lyric text.
- If a transliteration already exists, the control should toggle its
  visibility instead.
- Transliteration takes time. It needs a real pending state, and the result
  should be cached (there's an IndexedDB lyrics cache in
  src/lib/offline-db.ts — getCachedLyrics/setCachedLyrics — and a Redis
  layer in src/lib/cache.ts).
- Pick a transliteration approach and justify it in a comment. Options
  include a library, an API, or Intl facilities. It must handle at minimum
  Japanese, Korean, Chinese, Cyrillic, Arabic, Hindi. If a script can't be
  handled, say so in the UI rather than returning the input unchanged.
- Rate-limit the endpoint (src/lib/rateLimit.ts has the pattern).

Both the original and the transliteration should be readable together — the
existing markup renders them stacked; make sure that still works with the
new highlight treatment from prompt 2.1.
```

# Phase 3 — Share studio

*The biggest remaining feature. Four prompts; do them in order.*

## Prompt 3.1 — Share flow & modal shell

```
Read § Shared Context in REMAINING-WORK.md first.

Replace the current share behaviour with a proper flow. Today sharing either
calls navigator.share with a bare URL or opens ShareModal
(src/components/ShareModal.tsx), and it's inconsistent per call site — the
mini player's context menu, the full player, the lyrics view and the track
page all do something slightly different.

Build the shell and the routing, not the renderers yet:

- One entry point every share site calls. MiniPlayer.tsx already dispatches
  a `sakura:share` CustomEvent with the track — either honour that or
  replace it with something better, but there must be exactly one path.
- A modal that first asks: image or video. Then branches:
  - Image → 5 distinct variations (built in 3.2)
  - Video → with lyrics / without lyrics, plus length and cover style
    (built in 3.3 and 3.4)
- "Video with synced lyrics" must only be offered when the track actually
  has synced or word-synced lyrics. Detect it, and when unavailable explain
  why rather than hiding the option silently.
- The final step shares: Web Share API with files where supported, download
  fallback otherwise, plus a copy-link path. Handle the cancelled-share-sheet
  case (it rejects with AbortError — that is not an error).
- Existing pieces to reuse or fold in: src/lib/shareCard.ts,
  src/lib/shareVideo.ts, LyricShareCard.tsx, LyricsPreviewCard.tsx, and the
  /api/shares endpoint with its /s/[slug] landing page.

Make the flow feel like one continuous thing — steps that slide, a back
path, and no dead ends. Generation is slow; the shell should be built to
show real progress rather than a spinner that hides everything.
```

## Prompt 3.2 — Image share variants

```
Read § Shared Context in REMAINING-WORK.md first, then read the share shell
from prompt 3.1.

Build 5 genuinely distinct image variants the user picks between. Canvas
rendering; src/lib/shareCard.ts is the existing starting point.

"Distinct" means different *compositions*, not one layout in five colours.
Think about what people actually post: a big-artwork card, a lyric-led card,
a minimal type-led card, something that uses the extracted artwork colour
(src/lib/color.ts already extracts an accent), something playful. Design
these — that's the interesting part of this task.

Requirements:
- Live previews the user can flick through before committing. Render at a
  sensible preview size and only produce full resolution on export.
- Export at a resolution that looks sharp on a modern phone, sized for
  social (square and story ratios both matter).
- Brand mark via drawBlossom/drawWordmark from src/lib/brandMark.ts. No
  emoji in canvas text.
- Fonts must be loaded before drawing or the first render silently falls
  back to a system font — use document.fonts.ready.
- Cross-origin artwork will taint the canvas and break toBlob. There's an
  /api/image-proxy route; use it.
- Long titles, long artist names, missing artwork, and RTL text all need to
  not break the layout.
```

## Prompt 3.3 — Video generation + trim

```
Read § Shared Context in REMAINING-WORK.md first, then read the share shell
from prompt 3.1.

Build video export. src/lib/shareVideo.ts exists as a starting point.

Two modes: with the song playing over a visual, and (in 3.4) with synced
lyrics animating. This prompt covers the base video plus the trim UI.

The trim UI is the part that has to feel good:
- A waveform the user scrubs to pick start and end. Real waveform data from
  the audio, not a decorative fake — decode and downsample.
- Draggable handles for both ends, with the selected region clear.
- Length presets alongside free selection.
- Live audio preview: as the user moves the handles, they hear that part of
  the song. This is the whole point of the feature — moving a handle in
  silence tells you nothing. Think about how preview interacts with whatever
  is already playing.

Encoding: MediaRecorder over a canvas stream is the pragmatic path; check
codec support properly (it varies a lot by browser, and Safari is the one
that will bite). Whatever you choose, document the tradeoff and fail
gracefully with an explanation rather than a broken download.

Constraints: export must not block the UI thread into unresponsiveness;
progress must be real; the user must be able to cancel; and audio must stay
in sync with the visual — drift is the failure mode people notice.
```

## Prompt 3.4 — Lyric video + cover-art styles

```
Read § Shared Context in REMAINING-WORK.md first, then read prompts 3.1–3.3.

Two additions to the video path.

1. Lyric mode. The video shows the lyrics animating in sync with the audio,
   as if the lyrics view were playing. Only available for synced or
   word-synced tracks (the shell already gates this). Design the motion:
   how lines enter and leave, how the active line is emphasised, what
   word-level sync looks like when the data supports it. It should feel like
   the app, not like a generic karaoke overlay — reuse the type and colour
   language from prompt 2.1's highlight treatment.

2. Cover-art styles. The user picks the visual treatment of the video
   background — a set of distinct looks built from the artwork. Design 4–6.
   Some ideas worth considering: blurred artwork behind a floating card, a
   rotating vinyl, an ambient field driven by the extracted accent colour,
   an audio-reactive treatment, something flat and typographic. Preview
   before committing.

Both must stay in sync with the audio for the full clip length. Test
against a long selection, not a 5-second one — drift compounds.
```

# Phase 4 — PWA

## Prompt 4.1 — Install prompt

```
Read § Shared Context in REMAINING-WORK.md first.

Add an install prompt. There's a manifest at public/manifest.json, a service
worker at public/sw.js, and src/components/SWRegister.tsx.

The requirement is that it be genuinely non-intrusive. A banner on first
load is the thing everyone does and everyone dismisses. Think about when

  specific and users look for that exact shape.

  navigator.standalone on iOS).
- Dismissal must stick, and stick for a sensible period rather than forever
  or one session.
- Once installed, the prompt should never appear again — listen for
  appinstalled.

Also audit the manifest and service worker while you're here: check the
icons cover what iOS and Android actually need, that the offline page works,
and that the SW doesn't serve stale HTML after a deploy.
```

# Phase 6 — Content and correctness

## Prompt 6.1 — Plain-language copy pass

```
Read § Shared Context in REMAINING-WORK.md first.

Rewrite the user-facing copy across the app for people who don't know how
software works. Right now a lot of it is written from the implementation's
point of view.

Sweep every page and component for: error messages that name internals,
empty states that say nothing useful, labels that assume vocabulary
("cache", "sync", "provider", "queue"), and buttons whose text doesn't say
what happens when you press them.

Principles: say what happened and what to do next; prefer the concrete over
the abstract; never blame the user; keep it short without being curt. Match
the product's voice — warm and calm, not chirpy.

Empty states deserve particular attention — they're the moments where
someone decides whether an app is worth using. Every one should offer a way
forward.

Also check the About page (src/app/(static)/about/page.tsx) actually
explains what Sakura is to someone arriving cold.
```

## Prompt 6.2 — Terms and Privacy

```
Read § Shared Context in REMAINING-WORK.md first.

Rewrite src/app/(static)/terms/page.tsx and
src/app/(static)/privacy/page.tsx, plus their stylesheets.

These need to be accurate first and readable second. Accuracy means you

third-party processors, user rights (access, export, deletion,

policy, and contact. Terms should cover acceptable use, account
termination, disclaimers, limitation of liability, and the fact that
third-party content is subject to its own rights.

Write in plain English with real headings and a last-updated date. Add a
short summary at the top saying what matters in a few lines — most people
won't read the rest.

Flag anything you couldn't determine from the code rather than inventing
```

## Prompt 6.3 — Frontend bug sweep

```
Read § Shared Context in REMAINING-WORK.md first.

Hunt for logic bugs across the frontend and fix what you find. This is a
correctness pass, not a style pass.

Several real bugs have already been found in this codebase and they suggest
where to look: a pseudo-element hit area that swallowed every tap on the
mini player; a velocity calculation that always evaluated to zero; a
router-cache replay that made onboarding restart forever; a theme value
("system") written into an attribute no stylesheet matched; a PATCH handler
that blanked fields it wasn't asked to change; settings whose display
strings were written into columns holding enum tokens; and several
fire-and-forget fetches with no error path.

Areas worth real scrutiny:
- src/components/PlayerContext.tsx (1914 lines — queue management, radio
  top-up, playback state sync, the resolved-id handling)
- Race conditions around async state: request ordering, aborted fetches
  landing after newer ones, state set after unmount
- useEffect dependency arrays and cleanup — listeners, timers, object URLs,
  IndexedDB transactions
- Optimistic updates without rollback
- Offline/online transitions (src/lib/useOfflineData.ts, offline-db.ts)
- localStorage reads that assume well-formed JSON
- Anything that can produce NaN or Infinity from a duration or progress
- Keyboard shortcuts firing while typing in an input

For each bug: explain what breaks, from the user's point of view, in the
commit or the comment. Fix the cause, not the symptom.

Report anything you find that you decided *not* to fix, and why.
```
